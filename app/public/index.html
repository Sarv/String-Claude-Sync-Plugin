What Claude Recall is
A personal, searchable memory of your Claude Code conversations.

            

              
While you work with Claude Code you ask questions, give tasks, and Claude explains what it did, what it changed, how to run it and what to watch out for. That explanation is valuable, but it normally stays buried in the chat.

              
Claude Recall keeps all of it. Every prompt you type and every text reply Claude gives is saved, with an embedding, in its own Elasticsearch indices. You can read any old session like a chat, open up to three side by side, and search across everything by meaning or by keyword.

              
    
                
  • No AI in search. Search returns the matching records as they were written. Nothing is summarised or rewritten, so you read the original answer.
    • 
                
  • Works for every project. One global hook covers every folder and session. Nothing is added to your projects.
    • 
                
  • Local by default. Everything runs on your machine in Docker. Ports listen on 127.0.0.1 only. It can also run as a shared server that several machines push to, each one approved by an admin (see Hooks → A shared server).
    • 
              

            

          


          

            
How it works
The hook pushes the new lines; the API queues them; a worker stores them.

            


Claude Code finishes a reply
   │  Stop hook (runs on your Mac)
   ▼
node scripts/hook.js      marks the session in ~/.claude-recall/pending + who is logged in, starts push.js, exits
   ▼  (detached, Claude Code never waits)
node scripts/push.js      reads the new lines after its own read position (~/.claude-recall/state.json)
   │  POST /api/push  gzip, ≤ 4 MB of complete lines per request   (+ device token on a shared server)
   ▼
API (app)  ── checks the range against what it has ── publish job, wait for RabbitMQ's confirm ──▶ 202
   ▼                                     (already have it → 200 DUPLICATE · a gap → 409 + the offset to resend from)
RabbitMQ  recall.ingest queue (durable: survives restarts)    retry after 10 s · 3 tries · then the dead-letter queue
   ▼  fetched by any free worker (2 by default)
Worker  ── Redis lock on the session (one worker per session at a time)
   │  writes only the lines after the saved read position (an earlier chunk not written yet → waits 2 s)
   │  keeps prompts + Claude's text replies, images, token usage (+ cost) · masks secrets
   ▼
Ollama (nomic-embed-text) → 768-number embedding per message
   ▼
Elasticsearch: claude_chat_log · _images · _usage · _prices · _projects · _users · _orgs · _memberships · _ingest_state · _settings
   │  read position saved only if nobody else moved it (if_seq_no)
   ▼  "changed" event (RabbitMQ fanout) → API → browser
This app: Chats · Search · Projects · Accounts · Stats  (open chats update live)

Local mode (default here): the workers can also read ~/.claude/projects from a read-only mount
(Sync page, auto-sync, startup catch-up). A shared server runs without the mount.

              
    
                
  1. Claude Code writes a transcript. It already saves every session as a .jsonl file under ~/.claude/projects. Claude Recall never changes these files.
    2. 
                
  2. The Stop hook pushes the new lines. After each reply, Claude Code runs scripts/hook.js. It notes the session (and who is logged in) in ~/.claude-recall/pending and starts scripts/push.js in the background, which sends the lines added since last time to the server. Details in Hooks below.
    3. 
                
  3. The API queues a job. It checks the pushed range against what it already has, publishes a job with the lines to RabbitMQ and answers as soon as RabbitMQ confirms it is saved. If the server is off, the lines simply wait on your machine and go with the next hook.
    4. 
                
  4. A worker fetches it. Workers are separate containers (two by default); each takes the next job. Before touching a session it takes that session’s lock in Redis, so two workers never write the same session at once; a worker that finds it locked puts the job back for 2 seconds.
    5. 
                
  5. The worker writes what is new. Claude Recall remembers how far each transcript is stored (the read position). Lines it already has are dropped, so a resend never duplicates; if an earlier chunk of the same session is not written yet, the job waits 2 seconds and tries again.
    6. 
                
  6. Filtering. It keeps your prompts and Claude's text replies. Tool calls and results, thinking, sub-agent chatter and slash-command plumbing are skipped. Images you paste are kept. Token usage of every API response is recorded, with its API-equivalent cost from the price table.
    7. 
                
  7. Embedding and indexing. Each message gets an embedding from the local model and is stored. The read position moves only after Elasticsearch accepts the batch, and only if nobody else moved it in between (a check on the document’s version), so a crash never loses messages and a worker whose lock ran out cannot overwrite newer work.
    8. 
                
  8. Done, or tried again. The job is removed from the queue only when it is finished. If the worker crashes, RabbitMQ gives the job to another worker. If it fails, it is tried again after 10 seconds; after 3 tries it goes to the dead-letter queue, shown on the Sync page with a Try again button.
    9. 
                
  9. Live update. The worker announces which sessions changed; the API passes it on, and open chats refresh.
    10. 
                
  10. Catch-up. If the server was down, the waiting sessions go with the next hook of any session. A session started before the hook was installed: node scripts/push.js --all sends every transcript. In local mode a sync also reads the transcripts from the mount (at startup, on the timer, or from the Sync page); a sync is a job too, one per file, shared by the workers.
    11. 
              

            

          


          

            
Hooks
What Claude Recall adds to Claude Code, why, and exactly how it runs.

            

              
A hook is a command that Claude Code runs on its own when something happens in a session. Hooks live in Claude Code’s settings file or come in a plugin, and apply to every project and every session on the machine, in the CLI and in the desktop app.

              
Claude Recall’s hook comes two ways, with the same code: on this machine, node scripts/install-hook.js adds it to ~/.claude/settings.json; on other machines it comes as the string-claude-recall plugin through managed settings (see A shared server below). Both share ~/.claude-recall/, so having both still sends everything once.


              
What is set

              
Claude Recall adds exactly one hook: a Stop hook. Nothing else in your settings is changed. No other hook events are used.

              

                
EventWhen Claude Code fires itUsed by Claude Recall?

                
                  
StopEvery time Claude finishes a reply (end of a turn)Yes: sends the transcript’s new lines to Claude Recall, and who is logged in

                  
UserPromptSubmit, PreToolUse, PostToolUse, SessionStart, …On every prompt / tool call / session startNo. Not needed: the transcript already has everything, and firing on every tool call would only add load

                
              


              
The exact hook

              
File: ~/.claude/settings.json (or $CLAUDE_CONFIG_DIR/settings.json). The installer writes this entry, with the full path to your node and to this project’s scripts/hook.js:


{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"/usr/local/bin/node\" \"/Users/abhimanyusharma/Documents/codes/nodejs/claude-chat-rag/scripts/hook.js\"",
            "timeout": 5
          }
        ]
      }
    ]
  }
}

              
    
                
  • type: "command": Claude Code runs it as a shell command on your Mac (not inside Docker).
    • 
                
  • command: absolute paths, so it works whatever your shell’s PATH is.
    • 
                
  • timeout: 5: Claude Code gives up on it after 5 seconds. The hook itself does no network at all and exits in a few milliseconds; the sending runs in a separate background process.
    • 
                
  • No matcher: a Stop hook has nothing to match; it runs for every session.
    • 
              


              
How one run works

              
    
                
  1. Claude finishes a reply. Claude Code starts the command and writes a small JSON payload to its standard input, for example:

    {
  "session_id": "9346042b-d7ae-4815-86fd-91a5c8ec5b15",
  "transcript_path": "/Users/…/.claude/projects/-Users-…-claude-chat-rag/9346042b-….jsonl",
  "cwd": "/Users/…/claude-chat-rag",
  "hook_event_name": "Stop",
  "stop_hook_active": false
}
    
                
    2. 
                
  2. scripts/hook.js marks the session. It reads who is logged in from ~/.claude.json → oauthAccount (only identity fields: account id, email, display and full name, organisation id, name and type, role and seat tier, plus Claude Code’s install id; no tokens or keys are stored there or sent; on an API key it is {"kind": "api_key"}) and writes ~/.claude-recall/pending/<session>.json with the transcript path and that account. Then it starts scripts/push.js detached and exits 0.
    3. 
                
  3. scripts/push.js sends the new lines. Only one runs at a time (~/.claude-recall/push.lock); a hook that finds it running just leaves its marker, and the running one picks it up. For each marked session it:
                  
      
                    
    • takes its own read position from ~/.claude-recall/state.json; if that file is missing or broken, it asks the server (GET /api/offset) instead;
      • 
                    
    • reads only complete lines after it (an unfinished last line waits for next time), up to 4 MB per request, gzipped, and posts them: POST /api/push with { slug, session_id, start, end, data }. The last request of a hook carries the account, which tags this turn’s messages;
      • 
                    
    • a single line over 10 MB (a huge pasted image) is skipped: the server is told to move past it;
      • 
                    
    • moves its read position after each accepted request, and removes the marker once the session is done.
      • 
                  
    
                
    4. 
                
  4. The API checks the range. It knows how far it has each session (queued, in Redis, or written, in Elasticsearch). Already have it all → 200 DUPLICATE. The push starts after that point (a gap: the client lost its state, or the server lost data) → 409 with the offset to resend from, and push.js resends from there. Otherwise it publishes a job { type: "push", slug, sessionId, start, end, lines (gzip), account, tenant_id } to recall.ingest as a persistent message, waits for RabbitMQ’s confirm, and answers 202.
    5. 
                
  5. A worker fetches the job (whichever is free) and:
                  
      
                    
    • takes the session’s lock in Redis (SET lock:session:… NX PX 30000, renewed every 10 s while it works); if another worker holds it, or an earlier chunk of the session is not written yet, the job goes back to the queue for 2 seconds;
      • 
                    
    • adds or updates the user, the organisation and their membership;
      • 
                    
    • stores the new prompts and replies, images and token usage (with its cost), each stamped with this account; lines it already has are dropped;
      • 
                    
    • links any messages of this session written since the previous hook that were stored without an account;
      • 
                    
    • saves the new read position only if its version is still the one it read (otherwise the job is tried again);
      • 
                    
    • releases the lock, removes the job from the queue (ack), and announces the change so open chats refresh live.
      • 
                  
    
                
    6. 
                
  6. If the worker fails or dies, the job is not lost: a crash leaves it unacknowledged, so RabbitMQ hands it to another worker; an error retries it after 10 seconds, up to 3 times, then it waits in the dead-letter queue.
    7. 
                
  7. The hook exits with code 0 whatever happened. A non-zero exit or output from a Stop hook could make Claude Code show an error or keep going; this one never does. What push.js did is in ~/.claude-recall/push.log.
    8. 
              


              
If something is off

              
    
                
  • App, RabbitMQ or Docker stopped: push.js tries 4 times (over ~13 s), then stops and keeps the markers. Claude Code is never affected. The next hook of any session sends everything that waited, with the account it was marked with.
    • 
                
  • No worker running: jobs wait in the queue (they are saved on disk) and run as soon as a worker starts.
    • 
                
  • Session started before the hook was installed: Claude Code reads hooks when a session starts, so that session doesn’t run it. node scripts/push.js --all sends it (in local mode, auto-sync stores it too).
    • 
                
  • Excluded project: the server answers EXCLUDED and push.js asks again at most once an hour. Nothing is lost: once it is included again, everything since its read position is sent.
    • 
                
  • Sent the same lines twice (a retry, a lost state.json, a job delivered twice): every message keeps its transcript uuid and the read position only moves forward, so nothing is stored twice.
    • 
              


              
Install, update, remove


node scripts/install-hook.js           # add it, or update an older version (the earlier curl one) in place
node scripts/install-hook.js --remove  # take it out; nothing else in settings.json is touched

              
Every change first saves a copy of your settings as ~/.claude/settings.json.bak-<date-time>. Running the installer again when the hook is current changes nothing.

              
Check it: node scripts/push.js --status shows the server, the device’s approval and how many sessions are waiting. In the app, the Sync page’s live log shows a hook: <project> › <session> line after each Claude reply.


node scripts/push.js --status   # server, approval, sessions waiting to be sent
node scripts/push.js --all      # send every transcript under ~/.claude/projects (first sync of a new machine)


              
A shared server (several machines)

              
A shared server has no transcripts folder: every machine’s hook pushes its own lines. Nobody hands out keys by hand; each machine asks once and an admin approves it.

              
    
                
  1. Start the server with an enrollment token per organisation (tenant) and an admin token:

    ENROLL_TOKENS=acme:<long random> ADMIN_TOKEN=<long random> \
  docker compose -f docker-compose.yml -f docker-compose.server.yml up -d
    
                  docker-compose.server.yml removes the mount and sets LOCAL_MODE=false and ALLOW_NO_AUTH=false. Put HTTPS (a reverse proxy) in front before opening it to the network.
    2. 
                
  2. Give every machine the hook as a plugin. The hook and the pusher are a Claude Code plugin, plugins/string-claude-recall, and this repo is its marketplace (.claude-plugin/marketplace.json, named string-tools). Push the repo (or just .claude-plugin/ and plugins/) to the GitHub repo Sarv/String-Claude-Recall (every employee must be able to read it). Then, as an Owner, paste this into claude.ai → Organization settings → Claude Code → Managed settings (or managed-settings.json via MDM). node scripts/install-hook.js --managed prints it:

    {
  "extraKnownMarketplaces": {
    "string-tools": { "source": { "source": "github", "repo": "Sarv/String-Claude-Recall" }, "autoUpdate": true }
  },
  "enabledPlugins": { "string-claude-recall@string-tools": true },
  "env": { "CLAUDE_RECALL_URL": "https://recall.example.com", "CLAUDE_RECALL_ENROLL_TOKEN": "<the token after acme:>" }
}
    
                  Claude Code picks the settings up within an hour, installs and enables the plugin at the next session start, and the employee can’t turn it off. Nobody copies files by hand.
                  
      
                    
    • Updates: raise version in plugins/string-claude-recall/.claude-plugin/plugin.json and push. With autoUpdate, every machine updates in its next session.
      • 
                    
    • Repo access: Claude Code fetches it with each user’s own git login (SSH key, or gh auth login + gh auth setup-git). For users without git access, use claude.ai’s GitHub/GitLab org sync, or host the plugin as a zip (archive source).
      • 
                    
    • Node: the hook runs node, so every machine needs Node.js 18+ on its PATH (Claude Code’s own installer doesn’t bring it).
      • 
                    
    • First start: Claude Code may show a security dialog for managed hooks and env. Declining it closes Claude Code.
      • 
                  
    
                
    3. 
                
  3. First hook on a machine: push.js makes up a device id and a secret (kept in ~/.claude-recall/device.json, readable only by you; the server keeps only the secret’s hash) and sends them with the enrollment token. The server answers APPROVAL_PENDING. Nothing is sent yet; the lines wait on the machine.
    4. 
                
  4. An admin approves it on the Devices page (it asks for the ADMIN_TOKEN). Until then every hook gets APPROVAL_PENDING.
    5. 
                
  5. After approval the next hook gets a device token (valid TOKEN_TTL_S, a day by default) and sends everything that waited. In the token’s second half the server hands a new one back; an expired one is replaced with the device secret, without a new approval.
    6. 
                
  6. Rejected (or an approved device revoked): its tokens stop working at once and the hook gets APPROVAL_REJECTED. It then sends nothing for the sessions it knew; a new Claude Code session on that machine asks for approval again, as a new device.
    7. 
              

              
Device status is kept in Redis (checked on every request) and in Elasticsearch (claude_chat_devices); tokens only in Redis, which is persistent. Every message, image, usage record and read position carries its tenant_id. Tenants are not kept apart in search and stats yet.

            

          


          

            
Using the app
What each page is for.

            

              

                
PageWhat you do there

                
                  
ChatsExpand a project in the sidebar, click a session to read it. Split pane (top bar), the pane icon next to a session, or Ctrl/⌘-click opens up to 3 sessions side by side. Drag the gutter between panes to resize, double-click it to make them equal. With 2–3 panes open, ← / → move to the pane on the left or right; ↑ ↓ and Page Up / Down then scroll that pane. Each pane opens at the latest message, follows new messages live, and has jump-to-top / jump-to-latest buttons. The trash icon in a pane header deletes that session.

                  
SearchType a question in your own words (Hinglish works). Filter by project and by who said it. Hybrid mixes meaning and keywords, Semantic uses meaning only, Keyword uses exact words only. Claude's replies show the prompt they answered. Open in chat jumps to that message.

                  
SyncSee every project found in your transcripts, how much is indexed and how much is pending. Sync all, sync selected, or one row. Exclude a project so it is never indexed. Turn auto-sync on or off and set its interval. Delete a project's data. Sync health shows the job queue (jobs waiting, how many workers), Redis, and failed jobs with a Try again button. A live log shows what the workers are doing. On a shared server (no transcripts folder) the sync buttons are off: hooks push the lines.

                  
ProjectsEvery project with its sessions, messages, images, tokens and cost. Search by title, folder or path; sort by recent activity, name, messages, sessions, output tokens or cost; 20 per page (10–100). Row actions: the chat icon opens the project’s latest session, the pencil gives the project a title (it then replaces the folder name everywhere: sidebar, chats, search, stats, sync; clear it to go back to the folder name), the trash deletes its data. Stats shows only the 10 most recently active projects and links here.

                  
DevicesMachines whose hook asked to push (shared server). Each shows who was logged in, the machine, its tenant, its status (waiting / approved / rejected), when it asked and when it was last seen. Approve lets it push; Reject or Revoke stops it at once. Needs the ADMIN_TOKEN when the server has one (kept in this browser tab only).

                  
AccountsTwo tabs, Users and Organisations (each with its count; ← / → switch them, and the last one you opened is remembered). Users: who has been logged in, their organisations and role, activity, tokens and cost. Organisations: members, activity, tokens and cost. The chart icon opens Stats filtered to that user or organisation. A note above the tabs says how many older messages aren’t linked to an account.

                  
StatsCounters (including API-equivalent cost), messages per day, tokens and cost per day, the hours you work, and tables: recently active projects (top 10), accounts, organisations, models and busiest sessions, each with its cost. Filter by account, organisation, project and date range (7 / 30 / 90 days, all time, or a custom range).

                  
SettingsChat text size (default 15 px) and theme, saved in this browser. Model prices: the price table used for cost (input, 5-minute and 1-hour cache write, cache read, output, a higher price for long prompts, fast-mode multiplier). Edit a model, add one, or Add known Claude prices (fills only missing models, never changes a price you entered). A model in use without a price is listed at the top with Add price. Saving recalculates every response’s cost.

                  
GuideThis page.

                
              

              
The sidebar button at the top left collapses the sidebar to an icon rail. While a page loads, grey placeholders show its shape. Syncs run quietly in the background and nothing about them appears on other pages. Open chats and sidebar lists update only when their own session gets new messages. The Sync page shows sync health, live progress and the log.

            

          


          

            
Key terms

            

              

                
TermMeaning

                
                  
ProjectA folder you ran Claude Code in. Claude Code keeps its sessions in ~/.claude/projects/<folder path with dashes>/.

                  
SessionOne Claude Code conversation, stored as one <session-id>.jsonl transcript.

                  
TranscriptThe JSONL file Claude Code writes: one JSON object per line (prompts, replies, tool calls, usage…).

                  
Stop hookA command Claude Code runs every time it finishes a reply. Ours marks the session and starts the pusher.

                  
Pushscripts/push.js sending a session’s new transcript lines to the server (POST /api/push), up to 4 MB per request, gzipped.

                  
Local modeThe server can also read ~/.claude/projects itself (a read-only mount): Sync page, auto-sync, startup catch-up and backfills. On by default here; off on a shared server (LOCAL_MODE=false).

                  
TenantWho a device pushes for, usually an organisation. Set by the enrollment token it used. Without a token (local) it is local.

                  
Enrollment tokenOne per tenant, given to every machine (e.g. in managed settings). It only lets a machine ask to push; an admin still approves each one.

                  
DeviceOne machine’s pusher: a device id + a secret it made up. Waiting for approval, approved, or rejected (Devices page).

                  
Device tokenThe short-lived key an approved device pushes with. Renewed by the server; kept only in Redis.

                  
SyncLocal mode: reading transcripts from the mount and indexing whatever is not indexed yet. On the auto-sync timer, at startup, or from the Sync page.

                  
Auto-syncThe timer-based catch-up (default every 5 min). It also runs once when the app starts. The hook works even when auto-sync is off.

                  
Job queueRabbitMQ. The API publishes jobs (a hook, a sync, a backfill, a cost recalculation); workers fetch them. Jobs are saved on disk and removed only when done.

                  
WorkerA container that fetches jobs and does the work: read transcript, embed, write to Elasticsearch. Run more with WORKERS=n.

                  
Session lockA key in Redis (lock:session:<project>/<session>) that a worker holds while it writes a session, so two workers never write it at once. It frees itself 30 s after a crashed worker stops renewing it.

                  
Dead-letter queueJobs that failed 3 times (recall.dlq). They stay until you press Try again on the Sync page.

                  
Read positionThe byte offset up to which a transcript has been indexed. Stored in claude_chat_ingest_state (written) and Redis recv:<project>/<session> (queued). Each machine also keeps its own in ~/.claude-recall/state.json (sent).

                  
PendingMessages present in transcripts but not indexed yet.

                  
Project titleA name you give a project (Projects page or Stats). Shown everywhere instead of its folder name. Stored in claude_chat_projects.

                  
ExcludeA project that is never synced (hook and timer both skip it).

                  
EmbeddingA list of 768 numbers that captures a message's meaning, made by nomic-embed-text. Similar meaning → nearby numbers.

                  
Semantic / keyword / hybridSemantic = nearest embeddings (kNN). Keyword = classic word match (BM25). Hybrid = both lists merged with reciprocal rank fusion (RRF).

                  
RedactionAPI keys, tokens, JWTs, private keys, password=… and credentials in URLs are masked before anything is stored.

                  
Account linkingTranscripts don’t say who was logged in. The Stop hook reads the current account from ~/.claude.json (ids, name, email, organisation, role; no tokens) and Claude Recall stamps it on the messages of that turn. Each message carries its own account, so a session that spans an account switch shows both. History from before linking stays “Not linked”.

                  
SidechainSub-agent work inside a session. Its messages are not shown, but its token usage is counted.

                  
Input tokensNew, uncached prompt tokens sent to the model.

                  
Cache writePrompt tokens written to the prompt cache (first time a long context is sent). Two kinds with different prices: 5-minute (1.25× input) and 1-hour (2× input). Claude Code mostly writes 1-hour cache.

                  
Cache readPrompt tokens served from the cache on later turns. Usually the biggest number, and much cheaper than input.

                  
Output tokensTokens Claude generated, including thinking.

                  
API-equivalent costWhat the tokens would cost on the Claude API at list prices (USD per million tokens, per model, from Settings → Model prices). On a Claude subscription you are not billed per token, so this is a yardstick, not your bill. Long prompts on Claude Haiku 5.5 (over 100,000 tokens, counting cache) are priced higher as a whole; fast mode multiplies the price (2× on Opus 5.5, Opus 5 and Opus 4.8); US-only inference adds 10%. A dated model id uses the price of the id without the date. Responses of a model with no price are left out and flagged with *. Known prices are Claude API list prices checked 17 Oct 2026; they are added on first start and a price you enter always wins.

                
              

            

          


          

            
Requirements

            

              
    
                
  • Docker Desktop with Compose v2. Works on Apple Silicon and Intel.
    • 
                
  • Memory: about 1.5 GB while idle (Elasticsearch ~1 GB with a 512 MB heap, Ollama ~330 MB, RabbitMQ ~100 MB, Redis ~5 MB, app ~20 MB, each worker ~20 MB).
    • 
                
  • Disk: about 1 GB for the Docker images, plus ~270 MB for the embedding model, plus the index (a few MB per thousand messages, more if you paste many images).
    • 
                
  • Claude Code (CLI or desktop app) writing transcripts to ~/.claude/projects.
    • 
                
  • Node.js (18 or newer) on every machine that runs Claude Code: it runs the Stop hook and the pusher after every reply (plugins/string-claude-recall/scripts/; scripts/hook.js and scripts/push.js run the same code), and the hook installer once.
    • 
                
  • Internet on first start to download the Docker images and the model, and for the fonts and icons the design system loads from CDNs.
    •

Messages, images and token records carry account_uuid and org_uuid; a session's read-position doc lists every account_uuids / org_uuids seen in it. What a device pushed also carries tenant_id. Every message keeps its transcript uuid as its id, so reading a file again never creates duplicates. A resumed session repeats earlier messages; those collapse into one record that belongs to the newest session.

            

          


          

            
Your data and deleting it

            

              
    
                
  • Claude Recall never edits or deletes transcripts: push.js only reads them, and in local mode they are mounted read-only.
    • 
                
  • Delete (pane header or Stats → Busiest sessions for a session; Sync, Projects or Stats for a project) removes Claude Recall's copy only: messages, embeddings, images and token usage. A project title and the price table are kept.
    • 
                
  • The dialog asks what should happen after deleting:
                  
      
                    
    • Keep it out (default): the deleted messages won’t come back on the next sync. New messages written later are still saved.
      • 
                    
    • Bring it back on the next sync: also resets the read position, so the next sync (or, for pushed sessions, the next hook, which is told to resend from the start) rebuilds it from the transcripts. Use this to re-index.
      • 
                    
    • Stop saving this project (projects only): keeps it out and excludes the project, so nothing new is saved. Include it again on the Sync page.
      • 
                  
    
                
    • 
                
  • Claude Code itself cleans up old transcripts after a while (30 days by default). What is already in Claude Recall stays.
    • 
              

            

          


          

            
Troubleshooting

            

              

                
You seeWhy, and what to do

                
                  
A project shows PendingA session is still running (the hook fires when Claude finishes), or it started before the hook was installed. Press Sync, or wait for auto-sync.

                  
New messages don't appear liveCheck the hook is installed (~/.claude/settings.json → hooks.Stop) and that the session was started after installing it. The status chip should say Ready.

                  
“Last sync never”Auto-sync is off, so the startup catch-up was skipped too. Turn it on in Sync, or press Sync all.

                  
Search is slow during a big syncThe query waits for the embedding model, which is busy embedding the batch. It is quick again once the sync finishes.

                  
“Service unreachable”The app container is down: docker compose up -d. Nothing is lost; the next start catches up.

                  
A cost has a *, or Stats says “responses have no price”Those responses use a model that is not in the price table (a new model, usually). Open Settings → Model prices: the model is listed at the top; press Add price, or Add known Claude prices if it is a known Claude model. Costs are recalculated when you save.

                  
The cost doesn’t match my billIt isn’t a bill. On a Claude subscription you pay a flat fee; the cost shows what the same tokens would cost on the Claude API at list prices. On the API, discounts (Batch) and other platforms’ prices (Bedrock, Google Cloud) are not included.

                  
Sync health shows Failed jobsA job failed 3 times (often: the embedding model or Elasticsearch was down). The error is listed under it. Fix the cause, then press Try again.

                  
Sync health says “No worker running”Jobs wait safely in the queue. Start the workers: docker compose up -d worker.

                  
Nothing arrives from a machineRun node scripts/push.js --status there and read ~/.claude-recall/push.log. APPROVAL_PENDING: approve it on the Devices page. APPROVAL_REJECTED: it was rejected; a new session asks again. ENROLL_TOKEN_INVALID: the token in managed settings doesn’t match ENROLL_TOKENS. server unreachable: the lines wait and go with the next hook.

                  
A machine’s first sync takes longA big history is sent in 4 MB pieces and embedded on the server, about a few minutes per 20 MB. Claude Code is never slowed down; follow it on the Sync page log.

                  
Changed EMBED_MODEL and the app stopsA model with a different vector size needs a new index. The message names the indices; delete them yourself, then restart to re-index.
